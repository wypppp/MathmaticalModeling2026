# 比赛作战手册（单人 + 多模型，5 天，目标特等奖）

> 新窗口的第一件事：读本文件、`AGENTS.md`、`state.md`。本手册汇总了两次演练（2026B、2026C）以及与 4 篇优秀论文对照后得到的全部规则。
> 演练材料在 `archive/` 下，需要时可以查阅；比赛期间不必回看。

## 0. 三条总原则

1. **人只做决定，不做比对和搬运。** 模型把一切整理成"带默认值的裁决单"，人只需回复"全部默认，除了 X"。
2. **共识解法只是及格线。** 各家大模型给出的架构与获奖论文的骨架几乎相同，拉开差距靠三样东西：①共识之外的洞察；②数值可信、执行质量高；③写作。
3. **简单强基线优先。** 复杂方法必须先在同一条件下赢过简单基线，才能成为主路线（演练 2：两阶段随机规划不比分位法好）。

## 1. 角色与工具

| 角色 | 由谁担任 | 职责 |
|---|---|---|
| 决策者 | 人 | 读题直觉、裁决、改写摘要和核心论证、最终提交 |
| **主工程方 + 整合者** | **本地 Claude Code**（可以使用 Gurobi） | 独立读题和建模、写代码运行、整理裁决单、维护 spec/state/evidence、起草论文 |
| 审查方 | GPT | 独立读题和路线；**审 spec 中的公式**；审核裁决单对它的转述；独立复算；审计 |
| 第三方（局外人） | Gemini 等其他来源的模型 | 盲点外审、路线发散、只看 spec 写测试、盲评论文。**必须给它数据摘要，并注明文件版本号** |
| 选题 | 你指定的那个模型 | 按 `process/选题方法.md` 独立完成，Claude Code 和 GPT 不参与 |

**协作方式：** 一切交接都通过 GitHub 仓库进行。GPT 推送到 `review/independent-*` 分支；第三方的产出由人贴进 `review/third_*.md`。

## 2. 时间表（5 天）与硬节点

| 时间 | 关卡 | 硬节点 |
|---|---|---|
| 第 1 天上午 | G-1 选题（不超过 3 小时）→ G0 读题 | — |
| 第 1 天下午至晚上 | G0 裁决 → G1 洞察 | **当晚 spec 冻结**；换题止损线在此 |
| 第 2 天 | G2 路线 → G3 预注册 + 回测器/检查器 + **全部问题的基线端到端跑通** | **第 2 天结束前，每一问都要有可交付的基线结果和结果文件** |
| 第 3 天 | 主路线；GPT 独立复算；第三方测试用例运行；G4 语义审计 | — |
| 第 4 天 | G5 敏感性、消融、异常搜索与洞察验收；**论文初稿完成** | 当晚停止新增模型 |
| 第 5 天 | G6 论文打磨、盲评、数字溯源、格式检查 | **截止前至少留 4 小时**用于排版和提交 |

论文从 G3 开始同步撰写：每完成一个结果，就把对应的段落和图写进 `paper/`。

## 3. 每一关的做法

### G-1 选题
- 由你指定的模型按 `process/选题方法.md` 完成（每题新开会话 → 自我反驳 → 倒序复评 → 一页报告）。人做决定，写进 `state.md`。
- 把题目原件放进 `problem/<题号>/original/`；运行 `python tools/data_digest.py problem/<题号>/original/附件 > problem/<题号>/数据摘要.md`。

### G0 读题（四方独立）
1. **人先读**，写 `notes/human_G0.md`。
2. Claude Code 和 GPT 各自独立写 `review/<模型>_G0_spec.md`：每条标出处，一条一行，并按 AGENTS §3.1 清单检查。
3. 第三方写盲点稿（附数据摘要，注明版本）。
4. Claude Code 整理 `review/G0_compare.md` 裁决单 → GPT 审转述 → 人裁决 → 生成 `spec.md` v1。
5. **spec 下发前，GPT 必须先审一遍其中的公式**（演练 2 中 Claude 写错的公式就是这样抓到的）。

**口径规则：** 题意有争议时，默认采用**字面最直接、多数队伍会用**的读法，另一种作为对照。如果 Claude 拟定的默认值与 GPT 相反，必须在裁决单中标为"人重点看"（演练 2 的 D10 就是反例）。

### G1 洞察（N1–N5 网格）
- 先写出"共识解法"。Claude Code 列出统一的行列清单；三方各自独立填满 N1–N5（见 `process/差异化洞察.md`）。
- **数据核查要用合理的基线方法**（演练 2 中"日内相关 0.97"就是朴素预测造成的假象）；结论用于建模之前，再核查一次。
- 裁决后 spec 升为 v2 并冻结。

### G2 路线
- 三方各自独立：先做结构分析，再列 6–8 个方向，推荐基线、主路线、挑战路线。
- **基线必须是简单强基线**，例如分位法、固定日末值、规则法；主路线要说明凭什么能赢过基线。
- 挑战路线只保留有限几项，例如 CVaR 敏感性；场景树、强化学习之类不做。

### G3 实现
1. **先在 `evidence.md` 预注册检验标准，然后才运行任何代码**（区分"可证明性质"和"经验预期"）。
2. 先写回测器或仿真器，以及**独立检查器**（不调用回测器的代码），再加单元测试，覆盖因果性、边界和解析算例。
3. **第 2 天结束前，所有问题的基线都要端到端跑通**，输出结果文件。
4. 每次运行都导出**未舍入的明细台账（csv）**，供 GPT 独立复核。
5. GPT 只看 spec 和结果，自己实现一份进行复算；第三方只看 spec 写测试用例，由 Claude Code 负责运行。

### G4 语义审计
- 第三方读 spec 和代码，**不给它讨论记录**，逐条核对代码是否偷偷放松了约束、单位或口径是否有误、边界是否处理。

### G5 验证与洞察
- 敏感性分析、消融实验、与强基线的配对比较（报告置信区间）、异常搜索。
- 洞察的验收标准：能改变数值并有消融对照，或给出可证明的结论，或能解释共识解法解释不了的现象。
- 第三方担任"结果质疑者"：只看结果表，找出不合理之处。

### G6 论文
- **摘要模板**（来自优秀论文）：每一问写一段，内容依次为：模型名称（加粗）→ 方法 → **具体数字结论**（加粗）；最后一段写总结和适用范围。
- **摘要和核心论证由人改写**，防止与使用同一模型的队伍雷同而被查重。
- 论文中的每个数字都要在 `evidence.md` 登记来源；图表由代码直接生成。
- 第三方担任盲评委：①只读摘要并复述结论（复述有偏差，说明摘要没写清楚）；②按评分细则逐项挑缺陷。
- 按论文格式规范检查；结果文件按模板填写；支撑材料包括代码和结果文件。

## 4. 两次演练提炼的硬规则

1. 原题以 `original/` 为准；PDF 中的图要渲染后查看（文字提取会丢失图中信息）。
2. 时间、单位、索引的对齐写进 spec（演练 2 的 D1：模板标签与数据错开 10 分钟）。
3. 观测推断：每一种观测能推出关于未知量的什么约束（演练 1：R ≥ d）。
4. 逐句删除测试：删掉这一句，题目会有什么变化（演练 1：允许圆外布点；演练 2：D8 的读法）。
5. 出题人给的"热身数据"（例如 1 月）、"指定日期"（例如二分二至）都有用意，但要**用数据验证**（演练 2：低负载日是周五和周六，不是日历上的周末）。
6. spec 中的错误会向下游传播 → 下发前由 GPT 审公式。
7. 交给第三方的材料要包括：数据摘要 + 文件版本号；并要求它先确认自己读的是哪个版本。
8. 第三方必须是**不同来源的模型**；同一模型换个会话几乎没有增量。
9. 报告的结果必须来自因果回放或真实执行，不能用优化器的目标值代替（随机规划的第二阶段会偷看未来）。
10. 神谕下界、强基线、本文方法三者并列，并做成本分解。
11. 预注册的预期一旦报警，必须给出解释，不能放过。
12. 凭记忆给出的数值一律标【待验证】；文献必须联网核实。

## 5. 回退与止损

- 关卡超时：降低复杂度 → 回到已验证的基线 → 缩小结论范围。**未通过验证的核心结果不得写成确定结论。**
- 第 1 天结束前发现选题有致命问题，可以换成第二选择；此后不再换题。
- 第 4 天晚上之后不再引入新方法，只做验证和写作。

## 6. 提示词模板（复制后替换 `<>`）

- **GPT，G0：** 读 main 分支的 `AGENTS.md` 和 `problem/<题号>/`（以 original 为准），独立写 `review/gpt_G0_spec.md`：每条标出处，一条一行，按 §3.1 清单检查（含观测推断、逐句删除测试）。不读 `review/claude_*`、`notes/human_*`。推送到 `review/independent-<题号>` 分支。
- **GPT，审 spec：** 读 `spec.md` v<n>，只检查公式、单位、计费口径是否与原题一致，逐条列出问题。
- **GPT，审转述：** 读 `review/G<n>_compare.md`，只检查它对你稿件的转述是否准确、有无遗漏。
- **GPT，G3 复算：** 不看 `src/`，在 `review/gpt_G3/` 下独立实现 <问题>，读取 `results/` 中的明细台账逐项复核，报告不一致之处。
- **第三方，盲点或路线：** 附上 `数据摘要.md`（版本 <提交号>）。先回答"你读的 spec 是哪个版本"，再按 <方法> 输出，每条一行并标出处。
- **第三方，测试：** 只读 `spec.md` v<n>，不看代码，写 15–25 个测试用例（边界、退化、对抗），每个给出输入和期望性质。
- **第三方，盲评：** 只读论文 PDF。①只读摘要，复述论文结论；②按评分细则逐项挑缺陷；③指出最不可信的 3 处。
